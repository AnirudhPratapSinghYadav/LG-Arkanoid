# Code Quality & Style Policy (LG Arkanoid)

The project must NOT look AI-generated. Write code exactly as an experienced university student and GSoC contributor would naturally write it after weeks of iterative development.

## Core Principles
- Prioritize readability, simplicity, maintainability, consistency, and clarity.
- NOT cleverness. Do NOT over-engineer.
- Do NOT introduce enterprise patterns unless objectively beneficial.
- Do NOT introduce abstractions without repeated need. Follow the "Rule of Three" (only abstract logic after it has been repeated multiple times).

## Human Writing Style
- Code should feel naturally written.
- Use meaningful variable names that explain intent. Avoid: temp, value, data, item, obj, newData, result1, test123.
- Functions should be small and focused (one responsibility per function). Avoid giant 300-line functions or functions doing multiple unrelated tasks. Prefer composition over complexity.
- Avoid unnecessarily long files, unnecessary nesting, deep callback chains, and premature optimization. Prefer straightforward control flow.

## Comments
- DO NOT generate AI-style comments (e.g., `// Initialize the game state`, `// This function is responsible for...`, `// TODO: Improve this later`).
- Write comments ONLY when explaining:
  - Liquid Galaxy specific logic
  - non-obvious algorithms
  - SSH behaviour
  - KML generation
  - protocol decisions
  - mathematical reasoning
  - important architectural decisions
- Assume future contributors are intelligent developers. Do not explain obvious code.

## No AI Signatures
- Never include text like "Generated by AI", "Created with ChatGPT", "Claude", "Copilot", "AI Generated", or "Auto Generated".
- Do not include robotic formatting or repetitive wording.
- Avoid identical code patterns across files.

## Error Handling & Logging
- Error messages should be human (e.g., "Unable to connect to the Liquid Galaxy master." instead of "Error occurred."). Include useful context and fail gracefully whenever possible.
- Logs should help debugging. Avoid meaningless logs like `console.log("here")`. Prefer descriptive logs like `Connection established with LG master.` or `Retrying SSH connection...`.
- Use log levels if appropriate, and remove temporary debugging logs before finalizing.

## Formatting
- Keep formatting consistent (spacing, quotes, imports, file organization).
- Do not randomly reorder code.

## Dependency Policy
- Never install libraries just because they are convenient.
- Every dependency must have a clear justification. Prefer native JavaScript/Node APIs whenever practical.

## Refactoring Policy
- Do NOT refactor working code solely for stylistic reasons.
- Refactor only when it improves maintainability, readability, testability, reusability, performance, or fixes a bug.

## Commit Quality & Open Source Friendliness
- Every proposed change should be small, logically grouped, and understandable in isolation. Avoid massive rewrites.
- Assume another GSoC contributor will read this code next year. Code should be easy to understand without additional explanation.
- Prefer explicitness over clever shortcuts. Optimize for maintainability rather than impressiveness.

## Final Code Review Checklist
Before considering any change complete, verify:
- [ ] No AI-style comments exist.
- [ ] No dead code remains.
- [ ] No unused imports remain.
- [ ] No console debugging statements remain.
- [ ] No duplicated logic remains.
- [ ] No unnecessary abstractions exist.
- [ ] No unexplained magic numbers exist.
- [ ] Every public function has a clear purpose.
- [ ] The code feels naturally written by a skilled student contributor.
